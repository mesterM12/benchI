# Local authentication foundation

Research for [GitHub issue #4](https://github.com/mesterM12/benchI/issues/4), current as of 2026-08-27.

## Decision

Use **Better Auth** with its email/password authenticator, database-backed sessions, and Admin plugin. Map Better Auth's default `user` role to benchI's domain term **Member** (or define a custom `member` role), and create the initial Admin with the Better Auth CLI during deployment.

This is the only candidate reviewed that meets all requirements in one in-process Next.js foundation: built-in password storage and lifecycle, revocable server-side sessions, Admin/Member-style RBAC, and a documented first-admin command, without a separately operated identity service. It is MIT-licensed and actively released. The tradeoff is a young, fast-moving project whose security policy supports only the latest release, so benchI must treat auth upgrades as routine security maintenance and apply generated schema migrations deliberately.

## Requirements and interpretation

"Fully local" means authentication data and execution remain on the self-hosted installation. "No external identity service" is interpreted strictly: an additional locally hosted auth daemon is operationally inferior to an auth library mounted in the Next.js process, even if it makes no cloud calls. A local application database is acceptable and necessary for users, password credentials, roles, and immediately revocable sessions.

## Security and operational assessment

### Better Auth

Use database sessions without `session.cookieCache` initially. Better Auth notes that cached session cookies can remain usable until cache expiry after server-side revocation; direct database validation preserves immediate revocation semantics ([session caching caveat](https://www.better-auth.com/docs/concepts/session-management#session-caching)). Configure `revokeSessionsOnPasswordReset: true`, because other sessions are not revoked on reset by default ([password-reset docs](https://www.better-auth.com/docs/authentication/email-password#revoking-sessions-on-password-reset)). Keep the secret outside the database and deployment artifact; Better Auth requires at least 32 high-entropy characters and supports rollover through multiple secrets ([installation](https://www.better-auth.com/docs/installation#set-environment-variables)).

The built-in `scrypt` choice avoids a native password-hashing dependency and is intentionally memory-intensive; Better Auth also permits Argon2. Using the default minimizes operational surface, while password policy, login throttling, TLS, backup protection, and authorization at every server-side action remain benchI responsibilities. Do not expose public sign-up unless the product needs it; the password configuration has `disableSignUp`, and Admin can create Members ([email/password configuration](https://www.better-auth.com/docs/authentication/email-password#configuration), [Admin create-user API](https://www.better-auth.com/docs/plugins/admin#create-user)).

Better Auth publishes advisories and commits to coordinated disclosure, but supports only its latest version ([security page](https://github.com/better-auth/better-auth/security)). That is acceptable only with an automated dependency alert, a prompt patch SLA, and migration tests. Generate migrations into source control rather than applying an unreviewed `@latest` CLI directly in production; the official CLI supports generation and migration ([installation](https://www.better-auth.com/docs/installation#create-database-tables)).

### Auth.js

Auth.js has sound session primitives: encrypted JWTs in `HttpOnly` cookies or opaque database session IDs, with the documented revocation differences between them ([session strategies](https://authjs.dev/concepts/session-strategies)). It is nevertheless the wrong abstraction for this decision. Its official credentials documentation explicitly leaves password persistence, encryption/hashing, rate limiting, and reset behavior to application code. Roles and bootstrap would likewise be custom. Selecting it would mean designing the security-sensitive foundation the issue asks to select, not adopting one.

Maintenance is active, but its owner now recommends Better Auth for new projects while retaining Auth.js security and critical-issue maintenance ([migration guide](https://authjs.dev/getting-started/migrate-to-better-auth)). That makes Auth.js reasonable for existing installations, not the strongest greenfield upgrade path.

### SuperTokens

SuperTokens is the strongest alternative if a dedicated local identity component is acceptable. It provides password login, sessions, and roles, and its stated backport policy is materially better than the latest-only policies of Better Auth and Auth.js ([README](https://github.com/supertokens/supertokens-core), [security policy](https://github.com/supertokens/supertokens-core/security)).

The cost is architectural: the official design has a frontend SDK, backend SDK, and Java Core HTTP service. benchI would operate, network, secure, back up, and coordinate upgrades across that Core and its database in addition to Next.js. Its security policy says Core is intended for a private trusted network and otherwise needs an API key. This is unnecessary complexity for a single local Next.js deployment and conflicts with the strict reading of no identity service. The open-core license boundary also requires checking that any future desired feature is not under `ee/` terms.

## Recommended implementation constraints

1. Pin Better Auth to an exact reviewed version and subscribe to its GitHub security advisories and releases.
2. Use the existing local relational database, database-backed sessions, HTTPS-only secure cookies in production, and a deployment secret of at least 32 high-entropy characters.
3. Enable email/password and Admin plugins; define `admin` and `member` explicitly if domain-language fidelity is worth the small customization, otherwise translate Better Auth `user` to Member only at the application boundary.
4. Disable public sign-up. Bootstrap exactly one initial Admin with `npx auth@latest create-admin` in a controlled deployment step after schema migration, then create Members through authenticated Admin operations ([Admin bootstrap](https://www.better-auth.com/docs/plugins/admin#usage)). Do not encode a permanent admin ID or default password in source.
5. Enable session revocation on password reset; avoid cookie session caching initially; authorize Admin operations server-side, not only in UI or Next.js middleware.
6. Review generated auth schema migrations, back up before applying them, and test login, role enforcement, session revocation, and first-install bootstrap on every upgrade.

## Conclusion

Adopt Better Auth. It minimizes custom security code and deployment surface while directly satisfying benchI's password, session, role, bootstrap, local-data, and Next.js requirements. Auth.js is too deliberately incomplete for password lifecycle and RBAC; SuperTokens is feature-complete but operationally disproportionate and service-oriented. Revisit SuperTokens only if benchI later needs a shared identity plane across multiple applications or requires a longer vendor-maintained security backport window strongly enough to justify another service.
